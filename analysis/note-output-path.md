# Arpeggiator gate expiry to output — 2026-10-12

## Gate Hold clock scope (2026-10-13 continuation)

Normal sequence service `FFF8BF3A` and Arpeggiator service `1C00091A` use the per-track advance frozen by Gate Hold in their running branches. The global-clock `FFF8CC18` route is an alternate service; it should not be treated as the sole ordinary sequence timer. Explicit release events can still clear shared source bits. See [gate-hold-control.md](gate-hold-control.md) for selectors, mask-processing differences, and limits.


## Result

The static trace now connects the Arpeggiator gate timer to MIDI message construction and to the CV/Gate state consumed by hardware register writes. The connection runs through shared note masks and queues. It does not require a direct call from the timer to an output driver.

Evidence: `note-output-trace.txt`, generated by `TraceNoteOutputs.java` using local Ghidra 12.1.4 and the existing mapped application. This is local static evidence, not REA Evidence or an observation of execution on the SQUID. Previously undefined function entries were disassembled in a read-only headless session; neither firmware nor saved project was changed.

## Recovered chain

`FFF8942C` establishes the mask-processing order through literal callbacks: `1C000740 → FFF8A808 → FFF8D0EC → FFF88AB8`, then `1C035484`. The comparison and queue-drain routines are separate services; their complete task/interrupt scheduling and latency have not been established.

### Timer active-note flag to output

The remaining static link is now traced. `FFF88C30` sets/updates per-track note bits in the active mask at `1C067060`, with timer values stored in `1C068360`. Per-track timer service `FFF8CC18` checks elapsed time and calls `FFF88D1C` when a note timer expires. `FFF88D1C` clears that note bit from `1C067060` and the associated mask at `1C067160`, and decrements the per-track active-note count at `FFF8E1D0`.

The callback loop starts at `FFF83288` (`movmu.l r8,@-r15` after the prior literal pool) and spans `FFF83288–FFF83425` and `FFF83494–FFF83635` around an internal literal pool. `FFF8335C` calls `FFF8CC18` for note-timer processing, then the loop calls `FFF8942C` to reconcile per-track note state. `FFF8942C` compares the current mask (`1C067060`) with its prior snapshot (`1C066F60`), runs the note-mask rebuild (`1C000740 → FFF8A808 → FFF8D0EC → FFF88AB8`), then publishes desired notes through `1C035484`. Later in the same loop, `FFF88E28` compares previous output notes with the published desired notes. Removed notes go to `FFF891BC` at velocity zero, are drained by `FFF8901A`, and reach `FFF87324`. That dispatcher routes MIDI, USB-MIDI, or CV/Gate; the CV/Gate release clears the sequencer source state and reaches the register writes described below. Ghidra's prior `FFF83386` function label was interior. `callback-loop-inspection.txt` records the corrected function body and assembly.

The vector `0xB0` handler `FFF87718` calls this loop through literal `FFF87920 = FFF83288` when its state branch has `FFF8DE74 == 0` and `FFF8DE76 == 0`, after a counter at `FFF8DE7A` exceeds `0xFFF` (`FFF87718` decompilation in `transport-window-inspection.txt`). The same handler later reaches the DIN consumer `FFF8526C` on its alternate state branch. This establishes an interrupt-service caller and code ordering, but the real time interval represented by the counter and any work by other tasks remain unknown.

This closes the static timer-active-bit → note release → MIDI/CV/Gate route question. The same callback loop also calls `FFF8897A`, which uses a separate timed-event ring and fills track-record bytes at offset `+0x23`. The `1C017844` formatter turns those bytes into MIDI Control Change (`0xB0`) messages, so that side queue is not the note-off queue. Exact runtime ordering and latency still need a hardware observation.

### Parallel timestamped event ring

`FFF8CA64` is a separate 128-entry ring producer at `FFF8ECDC`, with 8-byte records and 7-bit head/tail indices at `FFF8F2FE` and `FFF8F2FC`. It copies a 16-bit timestamp and three other bytes from shared state at `FFF8F308`, followed by the supplied track, note and velocity. It refuses to enqueue when global `FFF8EBCC` is nonzero or when advancing the producer index would meet the consumer index. A full ring therefore drops the event rather than overwriting unread records.

The call is conditional on `FFF8E440 == 1` (`FFF89146`), and the same global is consulted by other Arpeggiator/output code. Consumer `1C034C30` drains the ring while not paused (`FFF8EBCC == 0`), advances the 7-bit read index, and dispatches each record to `1C034724` when byte `+6` is zero or `1C034602` otherwise. The release insertion uses byte `+6 = 0`, so its queued copy takes the first handler. `1C034724` matches a track/note slot using a bitmap, reads per-step timing at track-object offset `+0x28e`, and can update that timing through `1C032FA4`. The examined handler does not call the MIDI/CV/Gate routing service. This confirms the parallel queue mutates shared track/step state, but whether that state later feeds the direct output path remains unestablished. This ring is distinct from the timed-event queue in `FFF88770`/`FFF8897A`, which feeds CC messages. The direct note output path proceeds through the per-track delay queue at `1C0661E4` and output records at `1C0669A4`.

## MIDI release representation

`1C0177FA` emits `[0x90 | channel, note, velocity]`. For the release event above, velocity is zero. `FFF87324` passes the formatted bytes to ring-buffer writer `FFF84F26` for routes 1/2.

`1C017930` emits `[0x09, 0x90 | channel, note, velocity]` for route 3; `FFF88266` copies these four-byte records into output buffers. This is consistent with USB-MIDI event packet formatting. The USB status-to-callback path and DIN register-feeding path are traced below; physical completion timing remains unobserved.

`FFF84F26` is a generic circular-buffer producer. Its descriptor carries read/write positions, capacity, wrap state and a storage pointer; it copies into the ring and advances the write position, incrementing a per-destination drop counter if space is insufficient. Note routes 1/2 call it with descriptors at `FFF8D9A0` and `FFF8D9AC`. `1C010B56`, called during initialization, only clears descriptor indices and a byte flag; it does not initialize a send engine. The wrappers `FFF87480` and `FFF85122` select ring descriptors and enqueue bytes. The output path can also invoke `1C01FBA8` before enqueueing; that routine checks MIDI status/channel filtering and may feed a separate four-byte USB-MIDI formatter path. `FFF88266` copies those four-byte packets into a rotating set of USB transfer buffers and marks a slot state byte `0x10`; this is evidence of USB-side buffer staging, but not proof of host transfer completion.

The USB-MIDI staging queue has a consumer at `FFF8812C`. It inspects the current slot (four slots, based on index masking), and when the slot state is `0x10`, endpoint/USB readiness checks pass, and length is one, it changes the slot state to `0x20`, signals endpoint 0/1 through `FFF879CE`, and advances to the next free slot. That state change is queued-to-handoff evidence: `0x10` is queued, `0x20` is handed off for submission, and zero length/state plus read-index advance is the release operation performed by `FFF87AB6`. The state names describe static code transitions, not observed bus timing.

The handoff continues through `FFF87A20`, which reads the shared mode flag `FFF8E08A`, selects the active payload/length ring, and passes that buffer to `FFF82104`. The latter records endpoint data/length in arrays at `FFF8F524` and `FFF8F574`, marks an endpoint transaction active at `FFF8F4E8`, and dispatches it via `FFF82156`. Setup helper `1C01F830` registers endpoint handlers; `1C01F964` installs `FFF87A20` and `FFF87AB6` for endpoint 4, and `FFF87A98`/`FFF87B4E` for endpoint 8.

`FFF87AB6` releases the slot after a completion-status dispatch: it clears length at `FFF8E074`, state at `FFF8E06E`, advances the four-slot index, clears `FFF8E08A`, and adjusts counters at `FFF8E094`. For mode 2 it performs corresponding operations on `1C064E44`/`1C064E4A`. Setup `1C01F964` passes `FFF87AB6` as the fifth argument to `1C01F830`, which stores that argument at `FFF8DFDC + endpoint*4` (`FFF8DFEC` for endpoint 4). `FFF87B4E` is separately registered for endpoint 8 and resets its descriptor payload/length/counter.

`FFF87B74` scans endpoint status and dispatches through `FFF8DFBC`. Registration stores the endpoint service argument (`FFF87A20`) at `FFF8DFB4 + endpoint*4`; therefore endpoint 4's dispatch entry is `FFF8DFC4`, the submit service, not `FFF87AB6`. Assembly at `FFF87BB4` loads that table entry and `FFF87BEE` calls it when status checks pass. The containing routine at `1C02014A` performs endpoint readiness/ack checks, then tail-jumps to `FFF87B74` at `1C020244`. This establishes the readiness/status-to-submission path. The separate completion/status dispatcher is `FFF87D3E`, described below. `FFF82156` selects lower endpoint service by endpoint type and calls acknowledgment/cleanup helpers such as `FFF82448`, `FFF82474`, and `FFF824C8`; those helpers alone do not establish transfer completion. `FFF8839C` only writes the shared transfer-mode byte.

Review correction (2026-10-12): `1C0201FC` is an interior call site, not a wrapper entry. The containing routine begins at `1C02014A` (`movmu.l r14,@-r15`), with a pointer to that entry at file offset `0xDF7C8` (runtime `1C02F7C8`). At `1C0201FA` it loads `FFF8812C`; `1C0201FC` calls it and sets `r14=1`. The same routine restores `r14` and jumps to `FFF87B74` at `1C020242–1C020246` when its conditions permit. A prior statement that no pointer to `1C0201FC` was found is therefore uninformative about callers of this routine. The call/entry distinction is visible in `transport-window-inspection.txt`.

The earlier targeted literal/xref scan missed two callback readers because their code was undefined in the saved Ghidra project. Bounded read-only disassembly established both: `FFF87D94` loads `FFF8DFDC` from literal `FFF87E60`, and `FFF88038` loads the same base from `FFF88128`. The earlier negative conclusion is superseded.

For endpoint 4, registration `1C01F966–1C01F974` passes direction 0; `1C01F830` writes the `(type=1, endpoint=4)` pair into the direction-0 table at `FFF8E016`. `FFF87D3E` reads that table, tests the associated status bit (`FFF87D74–FFF87D8A`), acknowledges it through `FFF829A6`, loads `FFF8DFDC + endpoint*4` at `FFF87D94–FFF87D9A`, and conditionally calls the nonzero pointer at `FFF87DAA`. For endpoint 4 that pointer is `FFF87AB6` at `FFF8DFEC`. This establishes the static status-to-release call edge. `FFF87FE4` performs the parallel direction-1 dispatch and uses the same callback base. Status values come from `FFF879FC(0/1)`, which reads `FFF8DFAC`/`FFF8DFB0`; the exact controller event represented by each status bit still needs hardware or lower-level register evidence.

The bootstrap at `FFF80036–FFF8003C` initially sets VBR to `FFF81800`. The original image has a populated initial table at file `0x1800`, omitted from the derived ELF. Runtime initialization at `1C024378–1C02439A` fills a table at `1C04E000` with the common dispatcher `1C024348`, then executes `ldc r4,vbr` at `1C02439A` with `r4=1C04E000`. Initialization routine `1C01C64E` registers 20-byte records through `1C02D032`. The record at `1C04235C` has vector index `0x80` and handler `FFF878E4`; the record at `1C042370` has index `0x84` and handler `FFF878EA`. Registration `1C02D032` builds the per-vector handler node and calls `1C0243E6` to install its dispatch entry. `FFF878E4` jumps through literal `FFF87960` to `FFF87D3E`; `FFF878EA` jumps through `FFF87964` to `FFF87FE4`. Thus the configured runtime vector chain reaches the two callback readers. The exact interrupt source naming and physical completion latency remain unverified.

For DIN MIDI, `FFF8526C` is the read-side consumer. Literal `FFF8541C` contains `FFF8D9A0`; its channel argument selects descriptor `FFF8D9A0 + channel*0xC`, hence `FFF8D9A0` and `FFF8D9AC`. It compares the read index at descriptor `+0` with write index at `+2`, loads a byte through the buffer pointer at `+8`, and calls `FFF8515C` (`FFF85306–FFF85314`, `FFF8536A–FFF85378`, `FFF85384–FFF853AC`). On a return of 1, branches to `FFF85220` advance and wrap the descriptor read index (`FFF85220–FFF85234`). `FFF8515C` tests status bit `0x20` at `FFFEB010` for channel 0 or `FFFEA810` for channel 1, writes the byte to base `+0x0C`, then clears status bits `0x20` and `0x40` (`FFF85164–FFF851CE`). `FFF87718` calls `FFF8526C(0)` and `(1)` at `FFF8787A–FFF87882` under its state checks. A configuration record at `1C042334` associates vector `0xB0` with handler `FFF87718` through `1C01C64E`/`1C02D032`. The read index advances when the byte is accepted for the hardware data register; an independent UART wire-completion callback has not been identified. `ring-reader-inspection.txt` contains the bounded decompilation and assembly. Physical transmission timing is not established.

MIDI 1.0 defines Note On with velocity zero as a note-ending representation; see the manufacturer-authored [Complete MIDI 1.0 specification](https://people.carleton.edu/~jellinge/cs312_w2020/pdf/_complete_midiSpec1_0.pdf), mirrored by Carleton. The recovered formatter therefore explains why searching only for a `0x80` Note Off status would miss this path.

## CV/Gate release and register writes

`1C0179D8` selects the last note/velocity pair in the current record and calls `FFF8678E(0x90,note,velocity,route-4,0)` through literal `1C017A44`.

`FFF8678E` updates pitch only for nonzero velocity. For status `0x90`, it writes `velocity != 0` to `FFF8DB72 + source*2 + output`. The sequencer call passes source zero. A release therefore clears byte `FFF8DB72` or `FFF8DB73` while retaining pitch.

`FFF861EA` consumes this state. Its final instructions at `FFF86626–FFF86650` implement:

```
gate1_bit = ((state[0] | state[2]) & 1) ^ (polarity[3] & 1)
gate2_bit = ((state[1] | state[3]) & 1) ^ (polarity[4] & 1)
```

Here `state = FFF8DB72`, `polarity = FFF8DB84`. `MOVI20` at `FFF861FA` loads `r9 = FFFE3810`. The final `BST.B` instructions write bit 4 at `FFFE3876` and bit 7 at `FFFE3877`. That address matches Renesas PDDR0, the 16-bit Port D data register, in both SH7264 and SH7269 pinmux maps; the SH7262/SH7264 hardware manual describes PDDR0 bits 15..0 as PD15..PD0 output data ([Renesas manual](https://www.renesas.com/en/document/mah/sh7262-group-sh7264-group-users-manual-hardware?r=1054966), [SH7264 register map](https://codebrowser.dev/linux/linux/drivers/pinctrl/renesas/pfc-sh7264.c.html), [SH7269 register map](https://codebrowser.dev/linux/linux/drivers/pinctrl/renesas/pfc-sh7269.c.html)). Since the application image is big-endian SuperH, the two byte bit-writes correspond to PD12 and PD7 if this peripheral mapping applies. This identifies the register class and likely pins, but the shared address does not identify the exact MCU, and the SQUID board's connector wiring is still unknown.

An expired sequencer gate does not necessarily force a particular voltage: another source may hold the ORed state active, and polarity changes the resulting bit. Track mode, preview and retrigger handling also matter earlier in the path.

## Analysis limits and reproduction

- Critical expiry and final register-write instructions were inspected alongside pseudocode. The zero-shift pseudocode anomaly remains: for example, the listing shows `mov #1,r6; shad r4,r6`, while pseudocode incorrectly renders the zero-index case as zero. Do not treat the recovered C as compilable source.
- The pointer scan covers initialized mapped blocks at two-byte alignment and references known to Ghidra. It does not exhaust computed aliases or uninitialized RAM pointers.
- New function entries were selected from a prologue after a return/literal pool (`FFF87324`, `FFF861EA`) or resolved function pointers (the formatter and CV routines). This improves code coverage without inventing runtime observations.
- No hardware capture, firmware modification or flash was performed. Physical MIDI transmission timing, transport completion, exact MCU identity and SQUID board connector wiring remain open. The static timer-active-note to routed-release path is traced; the separate timestamped ring's relationship to output remains unresolved.
